## Decision: ROI预选采用同快照的有界扩容，最终沿用Python公式

**Context.** 毛回报率预选会漏掉最高ROI；改为不取整ROI SQL后，近值仍可能因Python按元取整反序。运行中全局费用变化也会破坏预选与最终计算的一致性。

**Decision.** SQL式从同一维州税档表生成，作为预选；本请求固定假设快照。最终按investment_metrics重算排序，只有误差界可认证的前缀才作精度保证，否则同筛选翻倍扩容，单轮到40,000即停并披露限制。回滚同时恢复指标及ROI/假设元数据。

**Reason.** 避免把近似预选当精确排序，保留现有单一最终业务公式；界定计算量，无法证明时如实展示范围，而不是默称全局最优。

**Consequences.** DEF-0007是部分修复；真实后处理预算、假设API原子性和40,000以外结果仍待核查。不能以一次PG SQL耗时替代端到端性能。详见 docs/MERGE_WAVE08_ROI_2026-10-01.md；未改车位数据、最终ROI公式或前端公式责任。

## Decision: 未知车位不等于零车位

**Context.** 原始 Car 缺失时旧导入将其写为 0，网页遂把未知显示为确有 0 个车位；真实 0 也存在。

**Decision.** 新导入保留缺失为NULL、记录0保留；新表列可空，旧库映射/迁移/回填取消。网页省略全部房源车位数，解释facts去掉car_spaces；数据、API和估值特征保留。明确房源车位要求给无法核验/未按车位筛选说明，公共设施/专名不当成自带车位；含义不明保留原文并条件式提示。refine保留未取消的核验记录，只有明确结构化取消或新搜索重置才清除。

**Reason.** 缺失与数值 0 的来源证据不同，混同会把不确定数据表述为确定事实。

**Consequences.** 网页不再把旧0表述为真实车位数量，但底层旧0来源仍不确定。v4主源码及实际前端合成Chrome有限检查通过；识别规则不能代表所有语言，真实LLM/模型/PG尚未验证。未知派生garage可能涉及专名时保留歧义并警告，不为清理强删地点。见 docs/MERGE_PARKING_INTENT_V4_2026-10-01.md。

## Decision: 文档按所有者的节奏更新,不是每次改动都更新

**Context.** 跨 Agent 交接协议要求"完成有意义的工作后维护共享文档"。照字面执行的话,
改一行 CSS 也要走一遍文档,所有者认为这是浪费。

**Decision.** **检查每次都做,写文档等所有者说「更新」。** 中间只用一行
`待更新:…` 记下欠账。唯一例外:新发现的**未解决问题**立刻写进 Known Issues,一行。

**Reason.** 延迟的文档更新是可追回的 —— 欠账那一行还在,下一次「更新」就能补上;
而没记下来的 bug 是真的会丢。所以只给"会丢的东西"留一条即时通道,其余按节奏走。

**Consequences.** 会话进行中 docs **允许滞后于代码**,这是预期状态,不是失误 ——
`AGENTS.md` §0 的优先级表本来就把代码排在文档前面。
另一个 Agent 接手时:**以代码为准**,并留意 docs 可能落后一两个任务。
不要把 `AGENTS.md` §3 的节奏规则改回"自动更新"。

## Decision: 每个数字都必须标明来源

**Context.** 系统同时输出三类数字:数据库里的真实成交数据、建立在行业惯例假设上的
测算值、机器学习模型的预测值。混在一起展示,用户无法判断哪个能信。

**Decision.** 三类在数据结构、措辞和视觉上全程分开:实测/法定用实心点、基于假设加
`~` 前缀、模型预测用菱形并强制带典型误差。LLM 的提示词里也逐条规定了三类各自的说法。

**Reason.** 这是整个项目相对"直接问 ChatGPT"的**唯一实质优势**。放弃它,项目就只是
一个套壳聊天框。

**Consequences.** 新增任何展示给用户的数字,必须先确定它属于哪一类,并走对应的标记。
不确定归属的数字**不要展示**。详见 NOTES「数字的三种来源,措辞必须不同」。

## Decision: 没有结果时的回答不经过 LLM

**Context.** 搜不到房源时,让 LLM 解释"为什么没搜到"是最自然的做法。

**Decision.** `graph._no_result_answer()` 用确定性代码拼出回答,中英两份都写死在同一个
函数里。这条路径**完全不调用 LLM**。

**Reason.** "没有结果"正是模型最容易顺口编出几套房的场合。让它不经过模型,就从根上
没有编造的空间。

**Consequences.** 加语言、改文案都必须改这个函数本身,**不能改成"让模型翻译一下"** ——
那等于把刚堵上的口子重新打开。

## Decision: 不修改数据集来"修数据问题"

**Context.** 曾发现 426 行房源地址是单元号(`9/204 …`)却标成 `house`,看起来是脏数据。

**Decision.** 一行数据都不改。查证后确认源数据没错(Kaggle 的 `Type='h'` 官方口径包含
villa/semi/terrace),问题出在我们把它译成了"独栋"。改的是中文标签,外加给模型增加一个
从地址派生的 `is_unit_address` 特征。

**Reason.** 两条。一是组员会重新下载数据覆盖这边,改了也留不住;二是实测表明源标注是
对的 —— 那 426 行的中位价是典型独栋的 0.66,和联排一致,改标反而会把对的改错。

**Consequences.** 以后遇到"脏数据",**先查源头再动手**。修复优先级:展示标签 > 派生特征 >
训练口径,数据本身放最后。详见 NOTES V9.4。

## Decision: 所有距离都是直线距离,不引入路网

**Context.** 用户常问"走路几分钟到车站"。

**Decision.** 系统只给直线距离,并在 `registry.UNSUPPORTED` 里把"步行/驾车时间"明确
列为不支持;距离测算功能在地图上画的是一根**直线**。

**Reason.** 没有路网数据。用直线距离冒充路程会系统性低估,而这类误差正好落在用户最
在意的地方。

**Consequences.** 不要用直线距离换算步行时间。距离测算的连线**不许画成弧线或带垂坠感** ——
造型可以借,语义不能借:弯的线会被读成"实际路径"。详见 NOTES V9.8。

## Decision: 抽象属性由一张注册表驱动

**Context.** 早期加一个"安静"这样的属性,要同时改提示词、评分、标签、前端五处。

**Decision.** `app/amenities/registry.py` 是唯一出处:数据源、证据项、权重、不支持项都在
这里。提示词片段、`/api/meta`、评分、英文标签全部从它生成。`tests/test_registry.py` 会
检查一致性,`app/i18n.py` 的 `check()` 检查英文标签有没有漏配。

**Reason.** 分散在五处时,"加了源却忘了改提示词"这类错误**不报错**,只是模型永远用不上
新数据 —— 要等演示时才被人发现。

**Consequences.** 加数据源/属性只改注册表。发现需要在别处也写一遍,说明抽象漏了,应该
去补生成逻辑,而不是手抄一份。详见 NOTES「抽象需求:一张注册表驱动全部」。

## Decision: 前端不复制业务公式,改用 `/api/recalc`

**Context.** 详情窗里两个假设可以就地改,改完要立刻看到总成本和回报率变化。最快的做法
是在 JS 里把公式再写一遍。

**Decision.** 新增 `POST /api/recalc`(无 LLM、不查库,只有算术),和编排层共用
`formulas.investment_metrics()`。

**Reason.** 分档累进的印花税、NOI、ROI 的分母口径都带着"为什么这样"的理由,并被
`tests/test_formulas.py` 逐条盯着。前端再实现一遍,等于把这些理由复制到一个没有测试的
地方 —— 两边哪天不一致,页面上的数字会**安静地**和后端对不上。

**Consequences.** 前端不许出现业务公式。需要新的计算就加端点或扩展
`investment_metrics()`。假设的取值边界也只有一处:`assumptions.bounds()`。详见 NOTES V9.7。

## Decision: 界面上"看不看得见"不许依赖动画或过渡

**Context.** 首屏示例词条最初写成"默认 `opacity: 0`,延时后 CSS 过渡淡入"。结果整屏词条
全隐形,而且不报错。

**Decision.** 凡是决定元素可见性的属性,**底色就是最终可见状态**;入场效果用不可过渡的
属性(如 `visibility`)或事后由 `setTimeout` 清理的临时类来做。

**Reason.** 实测某些运行环境里动画和过渡的时钟根本不走(`currentTime` 恒为 0),
"从 0 淡到 1"的结果是永远停在 0。同类问题在这个项目里出现过五次:平滑滚动三次、地图取景
一次、首屏词条一次。

**Consequences.** 写动画前先问:它不播的话,界面还对不对?不对就换写法。
地图取景一律 `animate: false`。详见 NOTES V9.9。

## Decision: 防幻觉提示词不翻译,只追加语言覆盖段

**Context.** 做中英双语时,`_EXPLAIN_SYSTEM` 里那九条防幻觉规则也面临要不要译成英文。

**Decision.** 规则保持中文原文不动,只在末尾**追加**一段"用英文写,并且这三处措辞照这样
改"。模型读中文规则、写英文输出。

**Reason.** 那九条是踩过坑逐句调出来的。提示词措辞一改模型行为就漂 —— 翻译一遍等于让
中英两种语言下的护栏强度不一样,而且没人能一眼看出差在哪。

**Consequences.** 以后加语言照此办理:追加覆盖段,不要重写规则本体。详见 NOTES V9.6。

## Decision: 网页界面不用 Streamlit

**Context.** 任务书原本设想用 Streamlit。

**Decision.** 改用 FastAPI + 单页前端(无构建步骤,三个静态文件)。

**Reason.** 逐字流式输出、可编辑的条件卡、常驻地图 + 可拖拽详情窗这几件事 Streamlit
做不到或代价极高。理由详见 NOTES「为什么不是 Streamlit」。

**Consequences.** 前端没有打包工具,也不引入框架。改界面就是改
`app/web/{index.html,app.js,app.css,i18n.js}`。

## Decision: 首屏沙盘离线烘焙,浏览器不算光

**Context.** 首屏要一座"精致实物模型"质感的白模城市。实时光照路线(实验页 v5–v24)
连续多轮达不到:幕墙竖梃与立面明暗是同一个量,靠调光分不开,画质上限被浏览器锁死。
所有者随后给出了关键约束:**画面是静止、不可交互的,可以用作弊手段**,但
**交付物必须是模型,不能是图片**("图片分辨率再高也是图片")。

**Decision.** 用 Blender + Cycles **离线把光烘成贴图**,网页端用
`MeshBasicMaterial`(无光照)显示烘好的 GLB。交付的仍然是三维模型,不是渲染图。

**Reason.** 把"算光"移到离线,浏览器主要做贴图采样和合成,保留烘焙画质并减少实时光照计算;仍有贴图解码、显存和渲染缓冲开销,不能用约 19MB 下载量推断运行内存很小。
这条路线满足"允许作弊"与"必须是模型"两个条件。

**Consequences.**
- **相机被锁死**:只能在烘焙时那个正交画框内平移/缩放,**不能旋转**,一旋转明暗就错。
  要换角度 = 重烘(约 25 分钟)。
- 资产约 19MB(含四张原始草坪覆盖图),放 `app/web/showroom/`;是否入库见 TODO Now。
- 制作端脚本在 `design/white-city/blender/`,逐次实验参数见
  `design/white-city/LIGHTING_V24_EXPERIMENTS.md`,工作流复盘见同目录 `RENDER_LESSONS.md`。
- `showroom.mjs` 与 `app.js` **互不引用**,只靠 `nw:query` / `nw:lang` / `nw:showroom`
  三个事件通信;无 WebGL2 或加载失败回退到原来的 SVG 城市。不要把它塞进 `app.js`。
- **2026-10-03:手机直接共用电脑版沙盘。** 保留原模型、贴图和构图,解除宽屏初始化/显示/交互门槛,不制作移动简化版;实机与性能验证边界见 `PROJECT_STATE.md`。DRACO 解码器保留原版本与许可证并改为同站加载,降低资产阶段对外部 CDN 的依赖;这不等于已确认 iPhone 故障根因。
- **iPhone 第一轮兼容处理只控制峰值与资源生命周期。** 使用单一 renderer、图像并发 2、单 DRACO worker 并安全清理、户型目标首次转场懒分配;保持原资产/分辨率/DPR/MSAA/构图。约 1.03 GiB 完整 GPU 贴图估算尚未解决,有限 Chrome 通过不能证明 iPhone 修复;进一步处理须先提交证据与方案,不得直接压缩降质或替换背景。

## Decision: 首屏取景由程序按包围盒和 DOM 实测位置算,不写死数值

**Context.** 相机锁死之后,"初始画面显示模型的哪一块"就是一组固定数值。固定数值换个
屏幕比例就不成立:要么模型出画,要么右下角露出户型样板的一角,要么最高的塔插进输入框。

**Decision.** `cityFrame()` 每次按**模型在相机平面上的包围盒** + **输入框的实测
`getBoundingClientRect()`** 算画框,约束是:整座模型(含桌面影子)完整露出、底部留固定
空隙、最高的塔落在输入框右侧,且**把鼠标视差能推动的最大距离一并算进去**。

**Reason.** 首屏要适配任意窗口比例,而"模型不能压住输入框"这件事取决于输入框在该比例下
的真实位置 —— 只有运行时能知道。

**Consequences.** 改首屏文案或输入框宽度会自动改变取景,不需要重新调数值。
约束互相打架时的优先级已经定死:**宁可让塔少让一点,也不把画框拉宽缩小模型**
(拉宽会在窄屏上留出大片空白);两者都不满足才整体退远。改这段前先看懂这个优先级。

## Decision: 城市视角整组隐藏户型样板,而不是在模型里把它们挪远

**Context.** 城市沙盘与四套户型样板烘在同一个宽幅画框里,两组模型只隔十几米。
城市视角的画框边缘会切到户型区,首屏右下角因此露出白模一角。

**Decision.** 网页在城市视角把**整组户型样板连同它投在桌面上的影子**一起隐藏,
转场时淡入。为此影子层在渲染阶段就拆成城市 / 户型两张
(`design/white-city/blender/render_v28_shadows.py`)。

**Reason.** 在模型里把户型区挪远要重烘一次(约 25 分钟),而隐藏是零成本且可逆的;
画面是静止的,隐藏在视觉上看不出来。

**Consequences.** 两组模型**不能同时出现在同一画面**。若以后要同框,必须改 `.blend`
里的位置并重烘,同时重出两张影子层。给沙盘加新物体时,记得它属于哪一组、影子在哪张图里。

## Decision: 多轮修改由模型报「本轮变更」,程序负责应用

**Context.** 早期 refine 让模型把整份条件重填一遍。模型会顺手改掉没提到的条件、把已删除的偏好
从旧对话里恢复、把「再热闹一点」理解成删掉安静。这些都不报错,只是安静地搜错。

**Decision.** refine 时模型只输出 `changes`(set / remove / relative / prioritize),每项必须带
用户本轮原话里逐字出现的 `source`;`refinement.apply_changes` 负责应用,任一项不合法就整轮拒绝
转澄清。提示词里的 refine 示例也必须是这个格式(`tests/test_planning.py` 检查)。

**Reason.** 「没提到的条件保持不变」「删除的偏好不能复活」这类约束能用代码保证,就不指望模型自觉。
逐字 `source` 让每项变更都能追溯到用户原话。

**Consequences.** 改解析提示词要当心:2026-09-24 实测,几处单独无害的措辞改动叠加后,
「不要安静了,改找最热闹的」的正确率从 8/8 掉到 1/8。改完必须跑 `tests/check_refinement_language.py`
(真实模型,约 17 次调用)和首轮搜索对照,不能只看离线测试。

## Decision: 安静↔热闹的相对调整:保留词条、分数此消彼长、只让系统推断的门槛

**Context.** 所有者要求:先找热闹的,再说「再安静一点」,不能直接去掉热闹词条,要热闹和安静的
分值一起变动。实测两者在候选里负相关(约 −0.34),但数据往往允许先变安静而不怎么损失热闹。

**Decision.**(取舍属性对来自 `registry.CONFLICTS`,目前只有安静↔热闹)
- 反向属性的词条**永远保留**,除非用户明确取消。
- 属性分数的「一点 / 更 / 明显」至少挪 **10 / 15 / 25** 分(所有者定「一点」= 10 分;要精确分数用条件卡)。
- 同样安静的房子里优先更热闹的:反向属性只降到数据要求的程度。
- 反向门槛若是**系统推断的**(`value_source=inferred` 且非 `required`),原门槛内凑不够 5 套时
  每轮让 10 分、最低 50,并在排序说明第一条写明;**用户明确给的分数或「必须」永不自动让**,只提示。
- 结果变少(1–4 套)照常展示和讲解,说明写进排序说明;只有 0 套才恢复上一轮(`turn_notice`)。
- 同一句里对反向属性的 prioritize(「稍微安静点,但还是要热闹」)视为重申保留,不改排序。

**Reason.** 推断出来的 60 分本来就不是用户的数字,让它小步让步符合用户意图;用户亲口说的数字
属于「每个数字都要说清来源」的范围,改它必须经用户同意。50 约为全库中位,再低就称不上热闹/安静。

**Consequences.** 新增取舍属性对只需加进 `registry.CONFLICTS`。`turn_notice` 的含义保持为
「本轮结果没变、只回确定性说明」—— `present` / `explain` 看到它会跳过,**有新结果时不要用它**。

## Decision: 首屏河面颜色按所有者效果图在网页运行时调色

**Context.** 所有者给了一张效果图定河面颜色(青绿)。它是网页截图经 AI 处理生成的:文字已被改动
(「实测」→「实况」),所以只能作颜色目标,不能当网页的真实输出来比。烘焙贴图里的水几乎无色。

**Decision.** 不重烘、不改 GLB:`make_water_masks.py` 从烘焙贴图生成水面遮罩,`showroom.mjs` 的
`gradeWater` 只对遮罩内像素做亮度映射 + 染色,锚点与色调量自效果图。验证方式固定为:网页用
`?debug=water` 定位水面像素,效果图按颜色取水面像素,两边按亮度分「水面 / 截面」比中位色。

**Reason.** 这是调色问题不是光照问题;运行时调色可逆、调参秒级生效,重烘一次约 25 分钟。

**Consequences.** 重烘台座或河道后必须重跑 `make_water_masks.py`(遮罩与贴图同一套 UV)。
比较两张取景不同的图时**不要按位置取样**:2026-09-24 就因此得出过「用户浏览器渲染偏深」的错误结论。

## Decision: 印花税用 2016–2018 的历史税率表,半元向下取整

**Context.** 现行维州税率表 2021-07-01 起多了「超过 $200 万:$110,000 + 6.5%」一档。代码里没有这一档,
看起来像漏了(2026-10-01 复查时差点被当成 bug 补上)。另一个疑点是半元的舍入:原代码用 `round()`(银行家舍入)。

**Decision.** 税率表**保持四档历史表**(2008-05-06 至 2021-06-30 的合同适用),不加 $200 万档;
取整按 *Duties Act 2000* s 28(1):取最近的整元,**恰好 .50 时取较低整元**,以千分之一元为单位整数精确计算。

**Reason.** 数据集成交期是 2016-01 至 2018-03,完全落在历史表的适用期内,用现行表反而时间口径不自洽。
半元向下的措辞在 2000 年原始文本(No. 79/2000)和现行授权版 v141 里一致,所以整个成交期都适用。
`round()` 在整数部分为奇数时会多算 1 元;浮点下本该恰好 .50 的金额还可能算成 .4999…。

**Consequences.** 全库 20,800 套里 134 套税额变化,每套最多差 $1;`roi_certified_prefix` 的
「取整误差 ≤ 0.5」前提不变。**若改用 2021-07 之后的成交数据,必须同时换表**(见 `formulas.py` 注释)。
`stamp_duty_vic` 不能依赖模块级 import:ROI 离线测试用 AST 单独抽出它执行。

## Decision: 地图底图用 OpenFreeMap 矢量瓦片 + MapLibre GL,栅格瓦片只作退回

**Context.** 所有者要求地图做成参考稿那种毛玻璃浅色质感(白路、浅灰地、淡绿地与灰蓝水面)。
OSM 标准栅格瓦片的配色烤死在图片里:粉色干道、路牌编号、密集住宅网格,CSS 滤镜只能整体褪色,
试过四组参数都达不到。CARTO 的浅色底图现在要求 API key(瓦片直接返回 "API KEY REQUIRED")。

**Decision.** 底图改为 OpenFreeMap(OSM 数据、免 key、免注册)的 positron 矢量样式,由 `map-glass.js`
在客户端逐图层改色、隐藏路牌,经 maplibre-gl-leaflet 挂进 Leaflet;图钉、取景、测距仍全在 Leaflet。
没有 WebGL、CDN 或样式取不到时自动退回 OSM 栅格瓦片(带浅色滤镜)。库懒加载,首页不付这约 800KB。

**Reason.** 质感要求只有矢量样式能满足;保留 Leaflet 避免重写图钉/测距/详情联动;退回路径保证
地图永远有底图。

**Consequences.** 署名必须同时写 OpenFreeMap / OpenMapTiles / OSM(ODbL)。配色在 `map-glass.js` 的
`C` 表里改,不要再给矢量画布加 CSS 滤镜(滤镜只作用于 `.osm-raster`)。依赖 tiles.openfreemap.org 在线。

## Decision: 公开仓库的发布范围

**Context.** 所有者要求组员下载即可运行,仓库公开。阻碍有三:房源库要从 Kaggle 下载 + 10–30 分钟生成向量;
